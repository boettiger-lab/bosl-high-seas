# Private Geo-Agent Deployment Workflow

This documents the **private repo** deployment workflow for geo-agent apps. It does NOT apply to public repos — those use the geo-agent-template which simply clones from GitHub at pod startup.

A geo-agent app may be private for different reasons, with different privacy requirements that stack modularly:

| Privacy need | Mechanism |
|---|---|
| Private source code / config | ConfigMap-based deployment (this doc) |
| Private data (S3 tiles, parquet) | rclone sidecar + credential injection |
| Restricted user access | oauth2-proxy authentication layer |

Each module is independent. An app can use any combination.

---

## Module 1: Private source code (ConfigMap deployment)

When the GitHub repo is private, the pod can't clone it at startup (no credentials). Instead, source files are bundled into a Kubernetes ConfigMap and mounted into the pod.

### Source files vs generated ConfigMap

**The golden rule:** `k8s/content-configmap.yaml` is **generated** — never edit it by hand.

| Edit these | Never edit this |
|---|---|
| `index.html` | `k8s/content-configmap.yaml` |
| `layers-input.json` | |
| `system-prompt.md` | |
| `stac/*/collection.json` (if bundling local STAC) | |

Regenerate the ConfigMap from sources:

```bash
bash scripts/generate-configmap.sh
```

The script uses `kubectl create configmap --dry-run=client -o yaml` to produce the YAML without touching the cluster. Example `scripts/generate-configmap.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."

cat > k8s/content-configmap.yaml <<'HEADER'
# DO NOT EDIT — generated by scripts/generate-configmap.sh
HEADER

kubectl create configmap <app-name>-content \
  --from-file=index.html=index.html \
  --from-file=layers-input.json=layers-input.json \
  --from-file=system-prompt.md=system-prompt.md \
  --dry-run=client -o yaml >> k8s/content-configmap.yaml
```

Add `--from-file=stac-<name>.json=stac/<name>/collection.json` for each local STAC collection.

### Deployment workflow

```bash
# 1. Edit source files (index.html, layers-input.json, system-prompt.md)

# 2. Regenerate ConfigMap
bash scripts/generate-configmap.sh

# 3. Apply to cluster and restart
kubectl apply -f k8s/content-configmap.yaml
kubectl -n biodiversity rollout restart deployment/<app-name>
```

**Common mistake:** running only `rollout restart` after editing source files. The cluster reads from the ConfigMap already in the cluster — not from git. Without `kubectl apply`, the pod restarts with old content.

## Module 2: Private data (rclone sidecar)

When the app serves private PMTiles or other data from a private S3 bucket, add a `rclone` sidecar to the deployment. The sidecar proxies S3 data locally so credentials never reach the browser.

```
Browser → nginx (/tiles/ location) → rclone sidecar → private S3
```

Nginx ConfigMap routes the `/tiles/` path to rclone:

```nginx
location /tiles/ {
    proxy_pass http://localhost:8080/;
}
```

The sidecar container in `deployment.yaml`:

```yaml
- name: rclone
  image: rclone/rclone:1.69
  args: ["serve", "webdav", ":s3,provider=Ceph,endpoint=$(S3_ENDPOINT):$(S3_BUCKET)/", "--addr", "0.0.0.0:8080"]
  env:
    - name: S3_ENDPOINT
      valueFrom: {secretKeyRef: {name: <app>-secrets, key: S3_ENDPOINT}}
    - name: S3_BUCKET
      valueFrom: {secretKeyRef: {name: <app>-secrets, key: S3_BUCKET}}
    - name: RCLONE_S3_ACCESS_KEY_ID
      valueFrom: {secretKeyRef: {name: <app>-secrets, key: AWS_ACCESS_KEY_ID}}
    - name: RCLONE_S3_SECRET_ACCESS_KEY
      valueFrom: {secretKeyRef: {name: <app>-secrets, key: AWS_SECRET_ACCESS_KEY}}
```

Private STAC collection JSONs should be bundled in the ConfigMap (via the generate script) rather than hosted publicly, so S3 paths stay off the internet.

If the system prompt needs S3 credentials for the MCP server, inject them at pod startup via `envsubst`:

```yaml
command:
  - sh
  - -c
  - |
    envsubst < /content/system-prompt.md > /usr/share/nginx/html/system-prompt.md
    envsubst < /config/config.template.json > /usr/share/nginx/html/config.json
    nginx -g 'daemon off;'
```

## Module 3: Restricted user access (oauth2-proxy)

When only authorized users should access the app, add an `oauth2-proxy` deployment in front of nginx. All requests are authenticated (e.g. Google OAuth with an email allowlist) before reaching the app.

```
Browser → HAProxy ingress → oauth2-proxy → nginx pod
```

Key points:
- The allowlist lives in `k8s/auth-configmap.yaml` (plain email list, committed to repo)
- OAuth secrets (client ID, client secret, cookie secret) go in a Kubernetes secret — never committed
- Exempt unauthenticated paths (e.g. `/stac/`) if the MCP server needs public access:

```yaml
# in oauth2-proxy args
- --skip-auth-regex=^/stac/
```

The ingress routes to the `oauth2-proxy` service, not directly to nginx.

## Troubleshooting rollouts

**Stuck rollout (>2 min):** likely a bad node. Check and delete the stuck pod — the old pod stays live (`maxUnavailable: 0`):

```bash
kubectl -n biodiversity get pods -l app=<name> -o wide
kubectl -n biodiversity describe pod <new-pod> | grep -A5 "Warning\|Failed"
kubectl -n biodiversity delete pod <stuck-pod>   # reschedules to a healthy node
```
